oh-my-db

API & MCP reference

HTTP API

Base path /api. Mutating routes (marked 🔒) require Authorization: Bearer <token> when OHMYDB_AUTH_TOKEN is configured; unset by default.

GET /api/clustersConfigured cluster names.
GET /api/graph/{cluster}?q=&column=&column_type=&match=&kind=&neighbors=Catalog nodes for one cluster (tables, views, materialized views, dictionaries, with labels). No edges. Optional q: substring match against name/database/labels (and annotation summary), or key:value for an exact label lookup. Column filters: same as find_tables. With annotations on: per-node summary/status and a top-level annotations hints block. neighbors=true: per-node upstream_ids/downstream_ids (direct neighbors by id).
GET /api/search?q=&column=&column_type=&match=&kind=&cluster=Cross-cluster search, same filters as find_tables (column repeatable), at least one required.
GET /api/entities/{cluster}/{database}/{name}Full entity detail: columns with types/comments, raw DDL, engine, attrs, labels. With annotations on: annotation plus per-column description/values.
GET /api/entities/{cluster}/{database}/{name}/relations?direct=Transitive upstream (data sources) and downstream (consumers). direct=true limits to immediate 1-hop neighbors.
PUT /api/labels/{cluster}/{database}/{table} 🔒Set a label. Body {"key": ..., "value": ...}.
DELETE /api/labels/{cluster}/{database}/{table}/{key} 🔒Remove a label.
POST /api/sync?cluster= 🔒Re-introspect and re-sync the catalog — all clusters, or one if cluster is given. Also pulls annotations when enabled.
POST /api/annotations/{cluster}/{database}/{name}/proposals 🔒Only with annotations.proposals on. Body {"patch": {...}, "rationale": "..."}: JSON merge patch against the table's annotation file, checked against the catalog (422 lists every problem), opened as a GitLab merge request or GitHub pull request. Same as propose_annotation.

MCP tools

Mounted at /mcp over HTTP, or over stdio via ohmydb mcp. Same reads as the HTTP API.

list_clusters()Configured cluster names. Call this first — get_schema_graph requires one of these.
get_schema_graph(cluster)Catalog nodes for one cluster, with labels. No dependency edges — call get_table_relations for one entity's upstream/downstream. With annotations on: summary/status columns and global/database annotations hints.
get_table(cluster, database, name)Full detail for one entity: columns with types/comments, raw DDL, engine, attrs, labels. With annotations on: annotation (description, grain, status, hints, relationships, examples) and column descriptions/values.
get_table_relations(cluster, database, name, direct=False)Transitive upstream/downstream entities. direct=True for only immediate 1-hop neighbors.
find_tables(query, column, column_type, match, kind, cluster)Search entities across all clusters; all filters optional (at least one), ANDed. query: key:value exact label lookup, else substring of name/database/label. column: case-insensitive name globs (*_id), match="all"|"any". column_type: exact type on the same column. Adds matched_columns. With annotations on: query also matches summary; summary/status columns.
propose_annotation(cluster, database, name, patch, rationale)Only with annotations.proposals on. Merge patch (maps merge, lists replace, null deletes) against the table's annotation, validated against the live catalog, opened as a merge request for human review. Returns the branch and MR URL.
Annotation file schema

Human-curated YAML in the annotation git repo (with annotations.enabled on), one file per table: <db>/<table>.yaml, path = identity. Every field optional; unknown keys are errors. Full reference: docs/ANNOTATIONS.md.

descriptionWhat the table is. First line = summary in listings and search.
grainWhat one row means, e.g. one row per client event.
status, use_insteadactive | deprecated; db.table to prefer instead.
ownerOwning team or person.
query_hintsList of gotchas: FINAL, sorting-key filters, units, dedup.
columnsMap by column name → description, values (enum meanings: map or list).
relationshipsJoin paths: to (db.table, same cluster), from_columns/to_columns (same length), optional cardinality, description.
examplesVerified question → sql pairs.
_global.yamlRepo root: version: 1, query_hints, ignore (regexes on db.table, no drift stubs).
<db>/_database.yamldescription, query_hints for the whole database.
 
# app/events.yaml
description: |
  Raw user interaction events from the web app.
grain: one row per client event
status: active
query_hints:
  - Always filter on ts (sorting key).
columns:
  ts: {description: "Event time, UTC"}
  event_type:
    values: {click: element click, view: page view}
relationships:
  - to: app.users
    from_columns: [user_id]
    to_columns: [id]
    cardinality: many_to_one
examples:
  - question: Purchases per day, last 7 days
    sql: SELECT toDate(ts) AS d, count() FROM app.events WHERE event_type = 'purchase' GROUP BY d

Quote values containing , or : inside {...}. Proposals patch this shape: maps merge, lists replace whole, null deletes.
